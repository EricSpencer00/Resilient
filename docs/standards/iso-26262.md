# Resilient and ISO 26262

Resilient is **not** an ISO 26262-qualified software tool. Qualification and
product-level safety acceptance have not been established by this documentation.

## Intended use and tool confidence

Define the compiler, verifier, certificate checker and other tools actually used
in the project. Evaluate tool impact (TI) and tool error detection (TD), derive
the tool confidence level (TCL), and document whether qualification is required
and the applicable method under ISO 26262-8:2018 Clause 11. Do not presume TCL3
from the language's purpose or infer qualification solely from ASIL C/D.

For each safety-relevant tool use, record potential failures, their effect on the
item, downstream detection measures, evidence that those measures work, and the
responsible reviewer. The result is specific to the intended use and baseline.

## Software evidence

Contracts and verification reports can contribute to software unit verification.
Integration tests and target tests must cover the behavior outside the modeled
subset, including error handling, timing, memory, interfaces and safety mechanisms.
Trace software safety requirements through architecture, implementation and
verification results, with documented coverage gaps and independent review.

The integrator retains responsibility for the safety lifecycle, HARA and ASIL
assignment, safety concepts, hardware/software interfaces, configuration and
change management, confirmation measures and the safety case.

## Evidence boundaries

An implementation-backed contract result applies only to the modeled semantics,
assumptions and supported subset. Check each certificate's `basis`: a
`clause-only` result is not evidence that the implementation satisfies the
postcondition. An `unknown`, unsupported or timed-out obligation is unresolved.

Replaying SMT-LIB2 checks the emitted formula. It does not independently validate
requirements, source-to-formula translation, compiler lowering, runtime behavior
or target hardware. Hashes and signatures support integrity, not correctness.
Runtime checks contribute evidence only when their presence and behavior have
been verified for the selected execution path.

## Preparation package

Use the [qualification evidence intake](../qualification-readiness) to record
intended use, a fixed toolchain baseline, requirement-to-test traceability,
reviewed evidence and unresolved gaps. Its checker reports inventory completeness;
it does not certify the compiler or approve a product.

## Reference basis

[ISO 26262-8:2018 — supporting processes](https://www.iso.org/standard/68390.html). Use the licensed standard and project assessment basis for exact objectives.
