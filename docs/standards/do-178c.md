# Resilient and DO-178C

Resilient is **not** a qualified DO-330 tool. This page does not establish
DO-178C compliance or approval of airborne software.

## Agree the certification basis

The applicant must agree the software level, applicable objectives and planned
verification credit with the certification authority. Determine tool qualification
need from the tool's use and the verification it replaces or reduces; determine
the applicable DO-330 criterion and TQL rather than assigning a universal TQL.
A runtime included in airborne software belongs in the software lifecycle scope;
it is not automatically a development tool.

Use the applicable DO-333 supplement when claiming formal-methods credit. Record
formalization, assumptions, soundness limits, traceability and complementary
verification. SMT replay alone is not independent verification of compiler output.

## Software evidence

Maintain requirements, design and implementation traceability; requirements-based
tests; structural coverage applicable to the software level; target integration
and timing evidence; configuration management; quality assurance; and approval
records. Contract results can contribute only to the objectives and scope agreed
in the plans. A contract coverage report is not an MC/DC report.

**Robustness testing support.** Contracts that *cannot*
be discharged statically can serve as instrumented oracles for robustness testing
when retained runtime checks have been verified on the selected backend. This
does not replace requirements-based tests or structural coverage.

## Evidence boundaries

An implementation-backed contract result applies only to the modeled semantics,
assumptions and supported subset. Check each certificate's `basis`: a
`clause-only` result is not evidence that the implementation satisfies the
postcondition. An `unknown`, unsupported or timed-out obligation is unresolved.

Replaying SMT-LIB2 checks the emitted formula. It does not independently validate
requirements, source-to-formula translation, compiler lowering, runtime behavior
or target hardware. Hashes and signatures support integrity, not correctness.
Runtime checks contribute evidence only when their presence and behavior have
been verified for the selected execution path.

## Preparation package

Use the [qualification evidence intake](../qualification-readiness) to record
intended use, a fixed toolchain baseline, requirement-to-test traceability,
reviewed evidence and unresolved gaps. Its checker reports inventory completeness;
it does not certify the compiler or approve a product.

## Reference basis

[FAA AC 20-115D](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_20-115D.pdf). Use the licensed standard and project assessment basis for exact objectives.
